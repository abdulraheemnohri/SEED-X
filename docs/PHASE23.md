# Phase 23 — Release Engineering

## Release workflow
- GitHub Actions builds the debug APK, unsigned release APK and unsigned Android App Bundle (AAB).
- CI uploads artifacts for review. Unsigned artifacts are not suitable for Play Store publication or direct trusted distribution until signed with a release key.
- Release signing credentials must be configured as repository/environment secrets by the repository owner. Never commit keystores, passwords or signing keys.
- The optional llama.cpp-enabled Android build remains a separate CI build path.

## Regression and security checks
- Host C++ configure/build/CTest.
- JSON catalog/schema sanity checks.
- Android debug, release APK and bundle compilation.
- Static manifest check that rejects high-risk permissions unless reviewed.
- Provider requests require HTTPS for public hosts; local HTTP is opt-in and restricted by app code to loopback/private IPv4/.local hosts.
- Provider credentials are encrypted with Android Keystore AES-GCM and are not included in diagnostic reports.
- Crash reports remain local and require operator review before a GitHub issue is opened.
- System 1 Guardian remains the authority for tool execution; model output cannot execute shell commands or modify Guardian policy.

## Release checklist
1. Inspect CI results and download artifacts.
2. Test install/upgrade, model import/load/unload, provider requests, cancellation, Guardian emergency stop, diagnostics and notification flows on physical Android devices.
3. Verify model licenses and provider terms.
4. Configure protected signing secrets and produce a signed release separately.
5. Review permissions and privacy disclosures before publication.
6. Publish release notes, checksums and support/donation links.

## Known gaps
- No signed APK/AAB is generated by CI until signing secrets and a release-signing policy are supplied.
- Instrumented physical-device tests, Play Integrity, native crash/ANR capture and automated dependency vulnerability scanning remain future work.
- A successful CI build is not a substitute for real-device validation.
